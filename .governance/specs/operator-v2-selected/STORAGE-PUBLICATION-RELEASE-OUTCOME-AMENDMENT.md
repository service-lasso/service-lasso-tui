# Held storage publication and release outcome completion

Status: PROPOSED for parent selection. This additive phase clarification does not authorize execution, SOURCE_GO, storage/native qualification or weakening original retained-record guarantees. Exact selected BLUEPRINT/CODECS originals and prior amendments remain immutable.

## Exact original clauses and actual callers

Selected BLUEPRINT79 requires bounded exact-context replacement/clear, immediate nonfatal storage warning, no asserted restart restoration when save fails, failed saveB retainingA, no lateA clearingB and no invented missing operation ID. BLUEPRINT81 requires preserving exact legacy2 raw bytes, trusted exact-operation root/action, complete validation plus exactold recompare before synced held atomic3 publication; its statement that any failure leaves2 unchanged applies without a named phase distinction. Existing CODECS saved-record state/retention rules remain mandatory.

Current fileOperationStore.publication invokes action under one held owner, then invokes close; every close error is currently joined with recordPublicationUnresolved. replaceRaw/clearRaw return only error. persistOperator returns nil replacement bytes on any error. Restore migration and the reducer consequently retain the old in-memory record even when the new record was already physically verified and durable before a final native Close failure. This is inconsistent with real effects and cannot be cured by declaring old bytes unchanged. Legacy Save/Clear share this publication path and must receive equivalent exact effect semantics rather than wrapping away the outcome.

Linux temporary writes, syncs, obtains F_DUPFD_CLOEXEC duplicate, and checks the original writer Close BEFORE returning the held prepared object. Windows temporary similarly duplicates a noninheritable held native object before the original writer Close. These original writer Close outcomes are prerequisites, not postcommit cleanup. Both implementations currently defer prepared/backup discard; those actual native close/delete outcomes must be captured instead of ignored. Linux publish performs held target comparison, exact prepared identity/body comparison, Renameat, exact published identity/body readback and parent Fsync; failures attempt held rollback and verification. Windows uses held native rename and exact identity/body readback, with original private preimage; its actual supported durability prerequisites and filesystem qualification remain unproved and must be implemented/qualified before any settled-durable receipt. Header recognition or API return alone is never such a receipt.

Actual outer close first closes the old target and later deletes publication exclusion/recovery entries and closes lock/journal/parent handles. Those closes occur after successful publication body/durability checks. Linux can retire the journal and parent-sync before its final journal/chain Close calls; Windows retires held named entries before final native handle release. Failure of a last parent Close cannot honestly recreate custody through an unowned path, prove native release, prove old-byte retention, or be retried merely because its descriptor value remains known.

## Explicit phase/effect algebra

The private store outcome carries exactly two independent dimensions: publicationEffect = unchanged | replacement_applied | clear_applied | unresolved; cleanupRelease = released | unresolved. It also retains bounded exact original/replacement raw bytes and the original expected-record comparison, plus private actual held owner identities and observed native error outcomes. These are internal owner custody, not new public DTO keys, filesystem authority or a guessed operation record. Public warning remains a selected typed storage/ownership error with no raw path/handle/error text.

unchanged is admitted only when effects did not begin, or an attempted replacement was rolled back under the same held ownership and exact original identity/body plus required durability were positively re-established. Every decode/validation/context/CAS/prepare/write/size/sync/duplicate/original-writer-close/prepublication-identity failure preserves the original named record and private original bytes. A temporary/release failure adds independent unresolved cleanup custody; it never turns absence or an unchecked rollback into unchanged.

replacement_applied is admitted only after exact new native identity/body readback and every supported platform durability prerequisite succeeds. clear_applied is admitted only after exact own expected-record comparison, held removal and supported durable absence proof. No later cleanup error retroactively changes those positively established effects to unchanged. An unproved postrename/readback/sync/rollback state is unresolved, not applied; original preimage/replacement and durable exclusive recovery ownership stay retained until independently resolved. Windows/Linux platform qualification remains mandatory for the actual mechanism.

The selected original failure-preserves-old guarantee remains absolute for publication failures that resolve unchanged. A settled applied effect with a later cleanup-release error is explicitly success of publication plus failure of cleanup, not a failed publication. It must be reported as both facts. This phase addition never authorizes ignoring, downgrading, guessing safe closure, or removing unresolved cleanup ownership.

## Caller and lifetime obligations

replaceRaw, clearRaw and legacy Save/Clear must propagate the typed actual outcome with the independent error causes. No generic wrapper discards a cause or inserts a contradictory publication-unresolved tag after a positively settled outcome. An unresolved publication cannot return asserted new saved bytes or asserted successful clear.

For replacement_applied, persist/migration retain and adopt the exact new admitted raw record in local model custody even if cleanupRelease is unresolved; show immediate persistent safe cleanup warning. For clear_applied, remove only the exact matching local saved record after its validated authoritative disposition; preserve independent release warning and private owner custody. For unchanged, keep exact old record. For unresolved, retain original and candidate evidence without choosing an unproved authoritative on-disk record; block unsafe overwrite/clear/replay and require separately authorized reconciliation. No lost-ID action is saved or inferred.

Native release ownership/errors survive record adoption, clear, view/service navigation, refresh and normal error replacement. The outer operation owner retains the actual original platform object identity, original Close outcome, phase and bounded private recovery body until genuinely resolved. It never treats a reused integer descriptor as original authority or reopens a pathname to fabricate recovery. A platform Close returning failure is not retried without explicitly selected platform semantics and original identity proof. Read-only UI remains useful; cleanup unresolved prevents new mutation/storage publication from discarding its owner. Startup must expose retained unresolved recovery safely, never silently remove evidence. Durable release-custody publication/exclusion and independent process-owner lifetime proof remain real source/native obligations; this proposal supplies no surrogate receipt or claim of implementation.

## Every native helper belongs to the same outer custody

This outcome applies to both Linux and Windows at every acquisition/read/compare/prepare/discard path, not only the final close wrapper. Actual acquireOperationStore fail closures currently invoke s.close() and discard its error; early root/child stat failures similarly close native objects without propagating release outcomes. Actual read() drops old target.Close, and rejected file read/stat/current-target paths discard file.Close outcomes. Windows currentTarget and preparedMatches defer CloseHandle without admitting that outcome. Linux/Windows prepared discard and preparation-failure cleanup drop Close, Delete or Unlink failures. These are concrete incomplete source callers, not hypothetical failures or proof of native cleanup.

Every such helper must return or retain its primary source/action error and each independent native release/delete outcome in the original bounded outer ownership object. A boolean identity helper cannot silently return true after a failed comparison-handle release; its result must include the private release error and original native identity. Acquisition failures must retain the partial held chain, original created exclusion identity where positively established and original error causes; an unheld or substituted pathname is never cleaned. Prepared discard must bind the actual original prepared identity and effects, capture actual deletion and Close separately, and retain any unresolved original owner without a second unqualified Close attempt. A root/parent handle stat failure that prevents identity proof remains unknown ownership rather than an invented matching identity. Every platform syscall close/delete/unlink site is in the complete source inventory and source/native failure matrix.

The shared outer wrapper must not replace those retained causes with storageError or manufacture unchanged after an applied effect. The live reducer and restoration/startup callers retain the private owner/outcome object independently of public warning text and exact saved-record bytes. Crash/restart release ownership and durable warning/exclusion need the actual selected platform protocol and independently observed owner lifetime; a in-memory pointer or generic receipt alone does not prove durable recovery. Until those obligations are implemented and native-qualified, the product may report retained uncertainty but must not declare cleanup complete or storage GO. This addition does not authorize release, native retry, publication, cleanup or execution.
