# Windows original stream routing method proposal 361

Status: proposal only. No routing body, runtime fork, remote duplication, signal or host effect is selected or executed by this document. Source360 remains the implemented frontier. The exact-two inherited-handle and full public argument domain remain unchanged.

## Concrete finding and rejected insufficient remedy

Current owner_windows.c creates a pseudoconsole unconditionally, supplies PSEUDOCONSOLE and exactly the duplex client and gate in HANDLE_LIST, and does not supply independent standard streams. Remote DuplicateHandle after suspended birth followed by application-init SetStdHandle/os.Stdout replacement is insufficient. Installed Go syscall globals capture GetStdHandle, os globals construct NewFile from those values, termenv constructs its global output from os.Stdout, and lipgloss captures that output before tea.init. Runtime write1 independently queries current GetStdHandle. Both kinds of use must agree from their first genuine use. Separate stdout/stderr and original absent/redirected behavior cannot be recovered by labeling a merged pseudoconsole byte stream afterward.

## Proposed earlier boundary and alternatives

A useful remote-duplicate method requires a source-owned native bootstrap BEFORE the Go runtime starts, rather than a Go package init hook. Proposed build direction, requiring a separate source-method disposition: a repository-owned selected-toolchain entry shim invokes a pre-runtime native bootstrap, then transfers to the unchanged selected Go runtime entry only after successful original-stream publication. It must use fixed static candidate backing, Win32 ABI calls without Go/TLS/CRT initialization assumptions, and retain native call originals. No installed toolchain mutation is proposed. The ordinary executable startup entries inspected are _rt0_amd64_windows -> _rt0_amd64 and _rt0_arm64_windows -> runtime.rt0_go; a real shim/link/export implementation and ABI proof for each supported architecture are missing developer work. Merely naming those entries does not establish a supported linking recipe.

Alternative A (late application/bootstrap init) is rejected for first-use semantics. Alternative B (STARTF_USESTDHANDLES plus additional inherited standard handles) changes the selected exactly-two inheritance contract and is not proposed for implementation without an explicit contract decision. Alternative C (remote patching undocumented child process parameters or PEB) is rejected: neither source/native API correspondence nor safe loaded-code/own-writer authority exists. The pre-runtime source shim is the only direction proposed here; it is not represented as already selected or fully ABI-qualified.

## Console semantics and independent public streams

Private pipes preserve raw bytes but do not make console APIs equivalent. A console source cannot be represented as an ordinary pipe while allowing unmodified GetConsoleMode/ReadConsoleInput/GetConsoleScreenBufferInfo to infer its capability. Proposed route therefore requires explicit source-terminal consumers in the owned BubbleTea fork, including actual input records, key repeats, modifiers, mouse, resize, code page, console modes and restoration. The existing Windows fork does not consume SourceTerminal for these paths. Actual coninput.NewStdinHandle calls GetStdHandle and ReadConsoleInput uses a console handle; its current conInputReader selection cannot simply be forced onto a pipe.

Original nonterminal stdin CONIN$ fallback remains conditional inside Program.Run after flag parsing and connection resolution. No bootstrap console query may turn a later Run-only failure into rejection of help/config/invalid-flag diagnostics. Original console output capability, size and VT setup must be supplied from actual independently retained public console operations, while stdout/stderr bytes have distinct capture and forwarding routes. Early termenv/runewidth console queries likewise require actual original capability correspondence before first use: proposed shim route alone does NOT establish this, because pipe GetConsoleMode fails. A selected dependency/source hook or genuine console-handle routing method must complete that relation. This is a concrete unresolved part of the proposed method, not permission for a virtual terminal Boolean or silent renderer change.

Pre-runtime private failure output is its own source occurrence; no attribution to original stderr may be invented from a merged ConPTY stream. Capture and disposition must retain private bootstrap failure separately while preserving independently eligible original diagnostic behavior. Complete native/raw worker/deadline service must continue concurrently; a synchronous private-pipe exchange must not starve raw capture or original deadline observation.

Normal LOCAL/FINAL/independent ACK and required terminal subjects remain live through their selected cuts. Parent may select investigation/implementation of an exact repository-owned runtime/dependency bootstrap hook once its complete ABI/init/console relation is supplied, or revise the exact-two inheritance method explicitly. No public-domain narrowing is requested. Independent Windows pending settlement, Linux complete-prefix/seal/ACK and build-plan work can continue. This document supplies no positive admission, native acceptance, SOURCE_GO or claim of complete useful Windows behavior.
